## Summary
This unit is the Rust presenter's root for the GPUI client: `screen.rs` builds the whole sidebar, sections, project rows over linked machines, the bot and room pages and the open thread for every view request. `thread.rs` turns the 32 index rows of a page into `shown.thread`. `merged.rs` folds this machine's, linked machines' and the registry's projects into one keyed list, and `mod.rs` is the `Routed`/`NotPorted` router. The code is careful about refusing instead of guessing, and I found no panics on event shapes. Every slice of a string by byte offset sits behind an ASCII prefix check (`api_say`, `att_split`, `short`). The main risks are about cost and locking, not correctness. The whole presentation, including file-system work (`find_named` walks a project tree five levels deep, `origin_of_root` reads `.git/config`), runs inside `policies.with_state`, which holds the policy `Mutex` that the agent line watchdog and folds also need. Each view rebuilds the merged project list two or three times, at O(projects x threads) each, and deep-copies the whole picture into an `overlay` that no client reads. `mod.rs` still describes and carries a helper fallback (dump file, `reads` routing, `ping`/`restart` forwarding) that can never run: `main.rs:158-160` always passes `NotPorted` and `helper_running=false`. Every refusal, including a deleted or missing thread, comes back as the retryable PRESENTER_UNAVAILABLE instead of STALE_VIEW. `docs/slim-thread-known-missing.md` is half out of date, and `docs/instant-ui.md` describes a JS web client and test files that do not exist.

## Cross-unit questions
- (answer to a) `present/screen.rs:343` `file.open` without `thread`: intended. `filelink::absolute` (filelink.rs:27-40) already resolves a relative link against the thread's root (`root_of`), so files/misc.rs:73 `link_path` would find nothing left to resolve. On Windows `absolute` produces `/C:\…` (it joins by `/` after `is_abs`), which the `sh -c` opener then gets. Owner of filelink.rs and files/misc.rs: is Windows meant to reach this path?
- (answer to b) Yes: merged.rs:159 sorts each project's threads by `activity` descending, then id ascending, for local, far and registry threads alike (local threads use `max(activity, created)`, registry ones the registry's `activity`). `key_of` can collide across machines through `short_name` truncation (Findings).
- (answer to c) Yes: it should be `stale`. See the finding at thread.rs:406. gpui hub.rs:263/390 loops on a retryable refusal before the first draw.
- (answer to d) No byte-offset slicing of client-supplied strings in screen.rs, thread.rs, merged.rs or mod.rs. `api_say` (`x[9..]`), `att_split` (`l[13..]`) and `short` (`r[..i]`) all slice after an ASCII `starts_with`/`find`. present/keys.rs:154 `model_short` slices `model[..i]` at a `find('[')` (safe) and `base[..1]` (base is in an ASCII family list, safe).
- data/mod.rs:242 parses replies with `bots::reply::of`, while the desktop uses `session::composer::reply_split` (composer.rs:20). Are the two parsers meant to agree on every `<in_reply_to>` block (the `chars=` count check exists only in the latter)?
- wire/mod.rs:235 sends a notice on every rev. Does the client re-request a full `view.update` for each one, so that every commit rebuilds every open window (the cost findings above multiply by it)?
