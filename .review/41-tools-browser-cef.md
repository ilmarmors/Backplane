## Summary
The unit is the Bun helper `backplane-browser` the hub drives over NDJSON (Playwright over a persistent Chrome profile at `<home>/browser-profile`, JPEG screencast per owner, an in-page teach recorder, attach to the GPUI client's CEF over loopback CDP) plus an older X11 child-window CEF host (`tools/cef/host.cc`) and its TypeScript driver (`cef.ts`). Command validation is reasonable: the hub picks `op`/`id`/`page` and strips them from agent arguments, the helper only takes the top-level `page`, the CEF host whitelists keys and rejects newlines, and engine switching is careful to keep the old engine until the new one is up. The main risks are about what the browser is exposed to. Both engines run Chromium without its renderer sandbox while agents browse arbitrary sites with the person's logged-in profile. Any download a page starts is treated as "the person's" and pushed to the desktop's Downloads folder, and the files pass through an uncapped temp folder that nothing cleans. Lifecycle gaps: a crashed renderer tab is never replaced, attaching to the client's CEF orphans the owner's own tabs, and console/outline data are uncapped. A large part of `main.ts` and `cef.ts` (the X11 CEF engine, `engine`, `restore`, `show`/`hide`/`shield`/`focus`, `frames`, `upload`, `download`, `pdf`, `cookies_clear`, `pages`) has no caller in the Rust hub, the CEF runtime installer is a stub, `tools/platform/windows-path.ts` is imported by nothing, and the helper's own tests are not run by any workflow, although docs say one is a required release gate.

## Missing tests
- Renderer crash: kill the tab's renderer (`chrome://crash` or CDP `Page.crash`), then `navigate` must work again on a fresh tab.
- Page-initiated download (`<a download>` clicked by script, no person input) must not produce a `download` event delivered to clients, or must be flagged as not from the person.
- `attach` then `detach` on an owner that already has helper tabs: the tab count in Chrome must not grow over repeated cycles.
- Recorder: a text field labelled "API key" or "token" must be recorded as `secret: true` with no value.
- `snapshot` on a page that logs a 1 MB string and has a very large DOM: the reply stays under a fixed size.
- `personDownload` failure path: a download that fails (connection reset) sends `{event:"download", error}`.
- CI job running `tools/browser/test/home.test.cjs` and `smoke.ts` (none of the helper's tests are referenced by `.github/` or `scripts/`).

## Cross-unit questions
- native/gpui/src/viewers/browser.rs:124: does the client save every `browser.download` into Downloads with no prompt? If it does, the page-initiated download finding is a real drive-by file write on the person's machine.
- native/host/src/term/browser.rs:169: `take_download` leaves `src` in the helper's temp folder when the move is refused (over 2 GiB, or the copy fails). Should it delete the file?
- docs/browser-cef.md:20 (`BACKPLANE_CEF_CDP_PORT`): the GPUI client's CEF opens an unauthenticated loopback CDP port with the person's profile (`~/.cache/backplane/cef-gpui-profile`). Do the client's reviewers consider other local users, and the hub's loopback-trust model?
- Loopback trust (map concern 2): agent-driven pages run in a browser on the hub's machine and can send requests to `http://127.0.0.1:<hub port>` and to the loopback MCP server. Do those endpoints refuse requests from a browser (Origin check, CSRF on non-GET)?
- native/host/src/term/browser.rs:104: the helper's stderr goes to `Stdio::null()`, so every `log()` (download failures, popup errors, CEF exits) is lost. Is that intended?

## Style nitpicks
- `safeOwner` maps different owners to the same JPEG file ("a.b" and "a_b"; "" and "shared"). Harmless with hub thread ids, but worth a note.
- main.ts imports `chromium` from ./playwright.ts twice, under two names (`chromium`, `pwChromium`).
- `switchEngineNow` changes `requestedEngine`, `allowStartupFallback` and `fallbackReason` before it validates the CEF parameters, so a rejected switch leaves `status` misreporting the engine that was requested.
- `CefEngine.start` picks a port with listen/close/reuse (cef.ts:72), which leaves a small time-of-check window. Asking CEF for port 0 and reading `DevToolsActivePort` would avoid it.
