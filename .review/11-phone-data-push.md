## Summary
The unit is the phones' protocol: `data/mod.rs` runs one select loop per socket (requests, log lines turned into pushes, streamed text, the hub's outbox, a 2 s look at linked machines), `ext.rs` maps about 130 requests onto the hub's own RPCs, `term.rs` and `machines.rs` add terminals and linked machines, and `push/` gates, books and sends APNs alerts. The push gate is careful: an order needs a private `Source`, the worker checks it again, events are masked before they are stored, tokens never reach a log, the curl config is 0600 in a 0700 folder, and a copy hub sends nothing. The data side is a thin and readable dispatch, but it reads state three different ways (the model, the policy state, and scans of the log's tail), and the tail scans are both wrong past their window and expensive. The main risks are: a lock-order inversion between the mirrors' lock and the policy lock that can hang the hub, asks that vanish from phones once they are 4000 log lines old, and a revoked phone that keeps receiving alerts because its push token is never dropped. Every request runs with the whole of a paired device's rights (a login shell in the home folder included) by stated design, so the device credential is the only line of defence. Several hub and app contracts disagree (a plot's "none" frame, `clientId` on `thread.create`, `title` on `project.add`), and the specification is missing the image requests and names requests the socket does not serve. Stream bookkeeping, slow consumers, the 40-minute APNs token cache and the per-commit and per-2-seconds work under the model lock are the remaining weak points. Tests cover the happy paths of most requests and the push rules well; limits, cursors, lag, slow sockets, revocation and the APNs signing code have none.
