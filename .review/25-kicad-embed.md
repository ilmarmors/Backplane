## Summary
embed.rs runs one GUI KiCad per hardware project: it decides stock or fork mode, starts the process in its own group and memory scope, shakes hands over KiCad's API socket, keeps a long-poll on the fork's event socket, publishes the session as the info key `editor.kicad.<digest>`, serves the twelve `editor.kicad.*` requests, and hands `kicad/ipc.rs` a route so agents' requests reach the open editor. The pure rules (frame kinds, warm policy, eviction, task-gate parsing) are small, readable and tested; the start retry and the exit-on-signal behaviour have real process tests. The weak side is the lifecycle around the person's unsaved work. Every hub exit kills each KiCad at once with no grace and no save, which the docs deny. The GUI route exists only while a session is `ready`, so while KiCad is starting or slow an agent's write is sent to a newly started headless KiCad on the same files. The event loop ends for good after six failed polls while the session lives on. A KiCad that stops answering can never be ended from Backplane, and several editor requests wait on KiCad inside the request and so stall the caller's whole connection. State is spread over the actor and about a dozen process-wide maps keyed by a project path that is normalised in some of them and not in others. No test covers a modified editor at hub exit, the not-ready routing, a refused close, or two spellings of one project. The requests are open to any authenticated connection, with window ids and the X display taken from the caller.

## Cross-unit questions
- Answered (from unit 03): does `shutdown_all` kill with no grace, and is unsaved work lost? Confirmed, first finding. TERM and KILL go out back to back (embed.rs:875-877); nothing saves or asks; on Linux PDEATHSIG kills KiCad even without it. Lock files stay behind, and a new hub sweeps them only for a session it has itself seen fail or restart (:1343), so the first start after a hub restart meets them and the pre-warm is refused by `project_locked`.
- Answered (from the coordinator and unit 53): `editor.kicad.attach` is accepted from any authenticated connection, not only a local one, and the hub does not check that the window id belongs to the caller's display or session; `display` is used as given. See the finding at embed.rs:2792. The far router does not carry it (`editor.kicad.*` is not in net/far.rs `METHODS`).
- Answered (unit 53): a `detach` without `keep` for an evicted container does not free that KiCad. The hub sets `container = 0`, sends `AttachToParent{window:0}` and keeps the session `ready` (embed.rs:1516-1530). It is closed later only if nothing is unsaved: after 300 s unused (`idle_victims`; the detach itself resets the clock), at once when a new start needs room past three, or 15 s after the last desktop client that used KiCad disconnects. With unsaved edits it stays until the hub exits. A session detached with `keep: true` whose container is later destroyed without a word stays `parked` with the dead id; the fork's ET_DETACHED sets `lost_parent`, so the next attach re-parents even into an equal id, and being parked it is retired by the same idle and app-gone rules.
- Answered (unit 53): `show` with `remount` has no cap, no rate limit and no merging on the hub (embed.rs:1462 excludes it from the local switch; :2108-2116 hides the frame first). The show numbering gives way to a newer show only while a `ShowFrame` waits on KiCad's task; the remount's `HideFrame` is outside it. See the findings at embed.rs:2731 and :1308.
- Answered (unit 42): embed.rs treats the event cursor as per KiCad process: each start reads from `since: 0` (:2416) and nothing adds a generation, so a name built from an event's `seq` can repeat after KiCad restarts for the same project.
- kicad/ipc.rs (unit 27): the headless servers (`srvs`) and `ks::digest` use the project path as spelled. Do two spellings of one project give two headless servers on the same files? And `retire` of a server that is still `starting` (ipc.rs:224) marks it stopped without stopping the process: its ready line is then ignored, so does it keep running on the project the GUI now holds?
- kicad/ipc.rs (unit 27) and the fork: after a GUI session ends, does a held headless server (Shutdown refused) read the files again before it serves, or does it serve its older document?
- Client (unit 53): does the hub socket have a read timeout? An editor request can hold the connection for up to 10 minutes (embed.rs:1308), and the 15 s beat is not sent meanwhile. Does a pane that does not hold the container ever send `editor.kicad.detach`, `frames` or `dialogs`?
- Guard (unit 29) and unit 03: how long does the guard wait between its stop signal and a kill of the hub? That is the time `shutdown_all` could use for a grace.
- hub.rs `set_info` (unit 01): the 256-key bound is shared by every module and no editor key is ever removed. Who is meant to clear keys, and what does a client see when a new key is refused?
- wire/mod.rs:228 (unit 02): requests are awaited inside the socket's select loop, so a slow handler holds pushes and the beat for that connection. Is that intended for handlers that "may take their time" (api.rs:20)?
- The fork (outside this tree): does `Close{CM_SAVE}` answer before or after it has written the files (the hub kills 800 ms after the answer, embed.rs:1554), and does a `--parent-pid` exit or SIGTERM write recovery data?
