## Summary
The unit holds the usage-limit failover (the pure planner in fallback.rs, the hub-side driver in driver.rs), setup's checks and one-press installs, the skill installer, the Improvements requests and the agent's settings proposal. The planner is careful and well tested: classification reads only error envelopes, a request never returns to an account or provider it left, holds outlive a restart as settings, and 24 end-to-end scenarios run the real actors against stand-in CLIs. The weak part is the hand-off between the actor and the driver's detached task (`spawn_act`): the restart that a failover owes exists only in memory, so a hub stop in the pause (up to 48 s per reconnect try) strands the thread, and the task's late `Cmd::Stop` can kill a turn that started in between. The way back after a failover only goes up the order, so a thread whose own provider is not the top of the order never returns to it. The agent tools `settings_inspect` and `settings_propose` cannot work on a default hub: they validate the order against a hard-coded model list that names Claude only. A stale remembered limit and a stale `fallback.input` can make a later, unrelated turn fail over or restart with the wrong "original request". The installers do what their header says (no administrator rights, digest checks for Codex and FreeCAD, vendor scripts run unverified over TLS), but have no time limit and no cancel. `onboard.check` (the question from unit 48) is not throttled or single-flighted, and the copy guard covers it only through `proc.rs`: agent CLIs are refused, the `--version` probes and a client-typed program path still run. No Critical or High finding; nine Medium.

## Missing tests
- A thread whose provider is second in the order (or not in it) fails over to the first and must come back when its own provider resets.
- `settings_inspect` and `settings_propose` through the MCP server on a hub with the default order and no `BACKPLANE_MODELS`.
- A hub restart during the reconnect pause, and between the Interrupted(failover) commit and the restarted turn: the thread is carried on or ends visibly, and a delegated parent hears of it.
- A message delivered while the limit batch is handled (a `Cmd::User` ahead of the driver's `Cmd::Stop`): its turn must survive.
- A queued turn (`start_queued`) that meets a limit: the restart text carries the queued text, not the previous message.
- A `run-…` thread with every account out and a known reset: resumed or reported ended.
- A remembered limit, then Stop, then a turn that fails for another reason: no hold, no switch, the real error shown.
- A process that exits after a transient error line with empty stderr; and a later unrelated failure on the same thread is not reconnected.
- `reset_words` and `from_stderr` with non-ASCII text whose lower case changes length (`İ`, `K`) before `resets`.
- `transient_text`, `classify` and `auth_failure` negatives: "prompt is too long: 215034 tokens", "tool call timed out", an MCP 401 in a failed result.
