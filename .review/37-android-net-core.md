## Summary
The unit is the Android app's connection layer. One object, `DataClient` (1,099 lines), owns the data/1 WebSocket, request and reply correlation, the lists and entries the screens draw, the disk cache, the outbox, alerts and the failover to a home hub; around it sit the pairing link parser (`Hub.kt`, `HubList.kt`), the QR scanner, the Hub rescue screen over plain HTTP, terminals, dictation audio, Google's loopback sign-in and the foreground service. The pure parts (HubList, Outbox, HubRescue, TermStream, QrFrames, GoogleLoop's rules) are small, tested against tables shared with iOS, and I found little wrong in them. Parsing is forgiving throughout, every socket callback hops to the main thread behind a generation check, redirects are refused where a credential is sent, and debug hooks sit behind `BuildConfig.DEBUG`. The risks are in DataClient's stateful code, which has no tests: the entry merge can put one id into a thread twice (a photo message that looked failed, then Retry), which crashes the keyed list, and the 25 s reply limit that starts this includes the upload. One 401 puts the app on the "pair again" screen and a later successful connection does not take it off. Liveness means "a complete text frame in the last 40 s", so one large frame on a slow link drops the socket; the unused `Hub` class in Hub.kt documents this failure and its fix. The device credential is in plain SharedPreferences with backups allowed, and travels in the URL query of the socket and file requests, in cleartext for a LAN hub. Hub.kt's `Hub` class and all of ScreenCache.kt are dead code from the earlier app. The six routed questions are answered in the rows marked Qa to Qf.
