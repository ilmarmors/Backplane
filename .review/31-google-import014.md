## Summary
The unit holds two lanes. `google/` signs the hub in to Google accounts with OAuth for installed apps (PKCE, a loopback redirect to the hub's own port, a client's own listener or a pasted address), keeps refresh tokens in the vault, talks to Google through `curl` under the copy guard, and gives bots' threads nine Gmail and Calendar tools with approvals. `import014/` plans what of a 0.14 log comes across (pure, by line hash), copies files, adopts devices, account profiles and, with keys, the vault and the Google sign-ins, and writes the lines through `Hub::import_lines`. Both are carefully built: the pure parts are small and tested, secrets stay off command lines and out of replies, header and path injection into Gmail and Calendar requests is closed, the old home is only read, the line-level re-run logic is exact, and no push or policy transform sees an imported line. The main risks are in what the approvals show and when they are skipped: a run creates and changes calendar events (Google mails the invitations) with no approval, the create and update cards leave out or cut the description, the HTML mail card is not the mail that is sent, and a session grant never ends. The tailnet hop forwards an authorization code to any ts.net host named by an unverified state, which leaks the code when the OAuth client is one an attacker knows (a client baked into a build, or 0.14's, which the import installs). In the import the file copy is the weak part: it stops at the first error, never completes a bot folder it began, and can hang on a FIFO; its summary also tells the person the Google connection stayed in 0.14 when its refresh tokens came across. Tests cover the intended paths well (a mocked Google, a fixture home, re-runs, responsiveness) and none of the adversarial ones below.

## Cross-unit questions
- Answer to (a), google/mod.rs:275: confirmed, see the Low finding on `navigation`. `Req.trusted` is true for any loopback peer (main.rs:154), so the hop branch passes a request through `tailscale serve`; `net::listener::is_owner_conn` is the check it means. The loopback branch does not use `Req.trusted` at all and so also passes the always-on tunnel's untrusted door. Nothing is gained beyond reaching `finish`, which still needs the state and a code bound to the verifier.
- Answer to (b), import014/mod.rs:225: not a bug. Every old line is cleaned in `plan::each_line_at` (plan.rs:120) before any decision, the rebuilt lines come from `serde_json`, `store::clean` is idempotent and `Store::range` cleans again on read, so the re-run hash matches. `filter_map` at 225 can only shorten the batch given to `fold_quiet`, which uses `first_seq` alone.
