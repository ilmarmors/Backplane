## Summary
The unit puts another process's windows (the embedded KiCad editors) inside the GPUI client's window. `native_child.rs` has three back ends: X11 on its own x11rb connection (container window, reparenting stock KiCad's top-levels, SHAPE holes, passive grabs, dialog centring), Win32 (WS_CHILD container, async positioning, an input "shield", hotkey and click replay), and empty stubs elsewhere. `kicad_pane.rs` is the pane entity: a 40 ms tick plus an X-socket wake thread that decide who has the keyboard, which frame is shown, pre-warm and hand-over, and the pop-out window. The X11 code is sound with respect to errors: x11rb returns errors instead of aborting, every reply is `.ok()`-ed, and error events are drained and dropped by `pump`, so a KiCad that exits does not crash the client. The unsafe Win32 code is mostly correct (callbacks get stack contexts for synchronous enumerations). The main risks are cost and focus side effects. In the steady state the tick calls `nc::report` on the shown frame, which captures every pixel of the frame (XGetImage, or a screen BitBlt on Windows) 25 times a second just to read a "mapped" flag. On X11 the tick also walks the whole window tree and interns atoms over many synchronous round trips per tick. On Windows, Ctrl+` is a system-wide hotkey that stays registered while another application is in front. The X11 chord grabs pick keycodes by keysym in any column, which takes over the wrong keys on non-US layouts. The pop-out window holds its own handle to the pane, so View or an Edit of another project while popped leaves an orphaned pane alive. The focus logic is a large set of run-specific heuristics with little test coverage beyond the pure helpers.

## Improvements
| Priority | Area | Proposal | Why | Effort | Trade-off |
|---|---|---|---|---|---|
| P1 | tick cost | Split `report` into `mapped()` for the tick and the pixel sampler for the script; cache atoms; walk for dialogs only on root structure events | Removes the 25 Hz capture and most round trips (findings 1 and 2) | S | none |

## Missing tests
- `tick` in the steady state does not capture pixels (a seam over `nc::report` or a counter) — guards finding 1.
- X11 keycode choice for chords on a mapping where ';' is shifted and '`' is a dead key (pure helper over a keysym table).
- The Windows hotkey is unregistered when another process owns the foreground while `keys` was true.
- Pop out, then View; pop out, then Edit on another project's thread: one live pane, popped window closed or emptied.
- `keep`/`take_kept`: KEEP eviction order, replacing the same window and project, and that `out` never names a container still kept.
- `cut` with overlays of zero or negative size and overlays that cover the pane exactly (the `over.retain(|o| *o != p)` path in `after_frame`).
- `kind_of_title` with a project name containing '-' or '—' and a translated KiCad title (non-English KiCad: every stock frame becomes MANAGER).

## Cross-unit questions
- H/kicad/embed.rs (unit 25): `editor.kicad.attach` takes `container`, `toplevel` and `display` from the client (kicad_pane.rs:835). Does the hub accept them only from a local client, and does it check that the XID or HWND belongs to the caller's display or session? A remote device holding a credential could otherwise name any window.
- H/kicad/comment.rs `RESERVED` and the fork's `BACKPLANE_EMBED::m_reserved`: is their order exactly `reserved_chord_index` (native_child.rs:75, indexes 0 to 10 and 63)? Nothing ties them together but comments.
- H/kicad/embed.rs: when the client evicts a kept container (`keep` past KEEP, kicad_pane.rs:951), it sends `editor.kicad.detach` without `keep` for the old project. Does the hub then free that KiCad (memory), and what does it do with a project detached with `keep: true` whose container the client later destroys on window close without telling it?
- Does the hub's `editor.kicad.show` with `remount: true`, sent every 1.5 to 2 s while a frame stays unmapped or unshown (kicad_pane.rs:690,712), have a cap? The client asks for as long as the condition lasts.

## Style nitpicks
- `rounded_md()` on the Try again and Open the KiCad app buttons (kicad_pane.rs:1019, 1023) goes against the project's square-corners rule.
- `#![allow(dead_code)]` at native_child.rs:10 hides any function the pane no longer calls (e.g. `container` without a key, `dirty_title`).
- An orphan doc line at kicad_pane.rs:32 ("The hub's frame kind for a rail page.") sits above `press_keeps`, and one at :449 ("The × on a job's bar.") sits above `dismiss_notice`.
- `eprintln!("GPUI_LOG ...")` on every `kicad_info` and every pane event without the debug switch (kicad_pane.rs:782, 1239) is noisy in a release log.
- Several near-identical root-walk loops (`top_levels`, `parked_on_root`, `centre_dialogs`, `open_dialogs`, `dialogs_over`) could share one iterator.
