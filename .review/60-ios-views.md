## Summary
These files are the iOS thread list, thread screen, composer, voice (dictation and always-on), the project viewer (Board, Schematic, 3D, Mech, Files, Browser, Diff, Review), the link grammar and the terminal emulator. The code is dense but consistent: decisions come from the hub's data, JSON decoding is lenient (`c.str`, `c.int`), and forced unwraps are almost all guarded by an earlier check. Link handling is sound: untrusted message text only reaches `dMdOpen`, which whitelists `http`, `https`, `mailto`, `tel` and the app's own schemes, and a pairing link from outside asks first. The terminal emulator is a faithful port of `vt.rs` and I found no index that can go out of range on hostile bytes. The main risks are (1) the always-on voice path after the hub routes a message to another thread, (2) main-thread cost in the preview and diff screens (whole-file split and non-lazy rows, an image decoded in `body`), (3) text the person typed being dropped on failure (review comment), and (4) file and Markdown previews that open any URL scheme. The question from the hub's voice reviewer is answered below: the app does not send `voice-target` after a route.

Answer to the voice question: `voice-target` is sent in exactly one place, `VoiceModel.open` (DataVoice.swift:222-225), which runs only from `DataThreadView.onAppear` (`open(id)`, DataViews.swift:890) and `onDisappear` (`open("")`, DataViews.swift:899), and only while `always` is true and the open thread has changed. Nothing in the `frame` handler (DataVoice.swift:174-216) reacts to a retarget by the hub: no `voice-target`, no change of `openThread`. So after "Bub, ..." is routed, the phone's own notion of the open thread is unchanged and nothing is sent; the hub's session keeps the routed thread (`retarget` in session.rs:178 changes `a.params["thread"]`), and the next message goes there until the person navigates. Android behaves the same (DataVoice.kt:147).

## Style nitpicks
- Many `try?` calls drop errors silently (`voice.stop`, `voice.act`, resolve/reopen, `improvements.project`).
- `DataViews.swift` is 1,537 lines holding the list, thread, composer, queue, work panel, order card, improvements and pairing sheet; `body` of `DataThreadView` is at "the type checker's limit" by its own comment (:877).
- `UIKitField` `onPasteImages` re-encodes pasted images as JPEG at 0.95 regardless of the original (DataViews.swift:968).
- `Vt.swift` `Par.o` case copies the accumulator on each byte (`case .o(var acc, ...)` while `p` still holds it): quadratic over a 4096-byte OSC, harmless but avoidable.
- Stray unused `hold` doc comment placement: the comment at DataViews.swift:1082 ("A run of tool calls as one line") sits above the work panel docs, not above `DataFoldRow`.
