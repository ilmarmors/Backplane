## Summary
The unit plans `thread.*`, `project.*` and `queue.*` requests as pure functions over a small fold of the log (`plan.rs`, `fold.rs`), commits the events and then runs the effects: the agents seam, the worktree job (`worktree.rs`) and a once-a-minute merge ticker (`merge.rs`). It also holds the folder picker (`fs.rs`), the project home snapshot (`home.rs`), `/give` (`give.rs`, `handoff.rs`) and the sidebar's row actions and drag order (`actions.rs`, `reorder.rs`, `key.rs`; `key.rs` is order keys and handles no key material). The planners are careful and well tested against the old hub's recordings. Git is always called with argument arrays or `"$n"` script arguments, branch names are sanitised and bases checked, and I found no shell or path injection: `home.rs` resolves links and stays inside the project, and `fs.*` is unrestricted by design (the picker). The main risks are in the parts written after the port. The merge ticker decides "landed" from reflog age and takes a thread's lanes from a text search of its tool calls, so it can settle threads that merged nothing and remove another thread's worktree and branch; a fork puts an old snapshot on top of today's upstream. The worktree lifecycle is incomplete: only threads the ticker itself marked merged are cleaned, any git error falls back to the main checkout, and `WorktreeRemoved` is not read by the read model or the agents' world. Thread deletion is a one-way flag that deletes nothing on disk and stops less than a settle does; a removed project comes back when its folder is added again. The fold lock is held across agent stops, `queue.steer` can drop a message, and the `worktree.base` setting is read through a fold that never stores it. Tests cover the planners well, the ticker only through its helpers, and none of the worktree job's failure paths.
