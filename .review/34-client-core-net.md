## Summary
The unit is the desktop client's connection to a hub: the start-up choice of hub (`hub.rs` `Config::parse`, `main.rs`, `launch.rs`), the socket and its reconnect and failover loop (`hub.rs` `connect`, `session`, `failover`), the hubs list and credentials (`hubs.rs`), pairing and the blocking HTTP helper (`pairing.rs`), the CBOR and view-delta decoders (`wire.rs`, `delta.rs`) and the Windows self-install (`install.rs`). The pure parts are in good shape: `hubs.rs`, `pairing.rs` link parsing, `delta.rs` and `wire.rs` are bounded, return errors instead of panicking on hub data, and are tested, several against tables shared with the phones. TLS is plain rustls with the system roots in both paths, there is no custom verifier, redirects are not followed, and credentials are written 0600 through a temp file (a protected DACL on Windows). The risk is in `hub.rs` `session` and `connect`: about 170 very long lines hold the whole request, paging, delta, stale-reply, reconnect and failover state machine with no test, and three of the findings below are state that is set on one path and not cleared on another. A history page in flight when the person clicks another thread leaves the window undrawn for the rest of the connection and the client asking the hub for the view in a loop. Failover to the home hub never starts when the hub in use times out (a sleeping machine), because each 5 s connect timeout restarts the 20 s clock, and once on the home hub the probe of the chosen hub blocks the socket loop for the system's connect timeout. The first-run chooser cannot take the hub's own pairing link. On the security side, the client sends the device credential of the hub in use to whatever address a `hub.offer` names with no check and no question, a pairing link can pair with an address other than the one the question shows, and a hard-coded tailnet address is the default hub. Failure reasons (TLS, version, size, a wrong token) all become one "Hub disconnected" line, and the back-off never returns to one second.

## Cross-unit questions
- Answer to (a), the socket URL with `token=`: it is built at hub.rs:211 and passed to `connect_async_with_config`; it is never logged by the client. The only log of a connection failure (hub.rs:184) replaces the token text with `<token>` before printing, and the errors tokio-tungstenite 0.28 returns here (Io, Tls, Http with a status, HttpFormat, Url without the address) do not carry the URL (from knowledge of the crate; its source is not on this machine). The token does travel in the query of a plain `ws://` request to any non-TLS hub, and `screens/attach.rs:36` and `screens/images.rs:63` put it in request lines too.
- Answer to (b): confirmed, see the finding at hub.rs:228; `viewControl` is never sent (no occurrence in the client).
- Answer to (c): `thread.create`, `thread.fork` and `bots.give` are never resent. They are product RPCs the hub names in a `view.action` reply; the client sends each once and forgets them on disconnect (`outgoing` cleared, hub.rs:186). What is replayed is the command channel: see the finding at hub.rs:217. Two "+" presses made offline become two `view.action new-thread` requests after the greeting; they are refused as `STALE_VIEW` unless the `view.open` reply is handled first, so the outcome is a race, and input past 256 is dropped.
- Answer to (d): confirmed, see the findings at main.rs:133 and screens/mod.rs:235. An offer from the home hub is ignored (`hubpick.rs:66`).
- Answer to (e): no. `hubs::plan` checks only that the url is http or https with a host and no userinfo; `pairing::takes` checks nothing. See the finding at hubs.rs:85.
- Answer to (f): a 401 at the handshake of a paired client is final (re-pair screen, loop ended); a 401 for the hub's own token, and every other failure, is retried for ever. See the finding at hub.rs:176. The guard answers 503 on `/ws` while the hub is down (`native/guard/src/run.rs:405`), so a restart is not read as revoked.
