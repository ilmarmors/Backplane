## Summary
The unit is the hub's file lane: the Files tab's listing, writes and downloads, `/img`, `/message-image`, `/webimg`, `/attach`, the hub's own git (status, per-turn checkpoints, revert, design-history steps, commit/push/PR), design review (BOM, checks, release), KiCad 10 export, and 26 embedded shell and Python scripts. Path containment for thread-scoped writes is careful and well tested (`fm::contained`, `ops.rs`, `mimg.rs`, the #960 boundary tests), and scripts quote their arguments consistently; I found no shell injection through file, branch or tag names beyond one unterminated `git push` argument. The main risks are elsewhere: first, the lane was written before "design files live on main" (cdf04ddb3) and still resolves a hardware thread's code worktree, so Review reports "no schematic", Checks pass without running ERC or DRC, and the Files tab's writes and downloads act on a folder other than the one listed. Second, every git the hub runs has hooks disabled, including Commit, Push and the turn-end design push, which breaks Git LFS and bypasses pre-commit and pre-push policies. Third, project-controlled paths are read whole with no size or type check, so a `.backplane.json` naming `/dev/zero` kills the hub. Fourth, a file link in an agent's reply reaches `open`/`xdg-open` on the hub machine with no type or location rule. Retention is missing throughout: attachments, image snapshots, PDF page renders, checkpoint refs and their objects are never deleted. Child processes have no time limit and no output cap, and an RPC is awaited inline on its connection, so one slow git or kicad-cli freezes that client. Questions from other reviewers are answered in the rows marked (a) to (e): (a) misc.rs:75, (b) mod.rs:56, (c) rv.rs:78, (d) rv.rs:153, (e) attach.rs:52. Tests cover the pure rules well but not hardware threads with a worktree, projects in a repository subfolder, concurrency on the private index, or hostile project files.
