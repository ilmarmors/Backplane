## Summary
The unit is the hub's event log (`store.rs`), the single writer task with group commit (`Hub::writer`), the read model, start-up checkpoints with build-time fold stamps, the CBOR codec and the view delta. The happy path is sound: one writer, one `write_all` plus `sync_data` per batch before any caller is answered, the model and observers applied in log order, a torn tail never read as a line, checkpoints trusted only on version, stamp and fingerprint, and a home lock (`hub.lock`, flock) taken in `main.rs` before the store opens. `cbor.rs` is well bounded (512 KiB frame, depth 64, 50,000 nodes, no allocation from a declared length, no 8-byte or indefinite lengths) and `delta.rs` is correct because the client names the base it holds and a new connection starts with no base; I found no defect in either beyond a quadratic scan. The stamp lists in `fold_inputs.rs` cover today's folds (every test module is at the end of its file, no fold reads the environment or the clock). The main risks are in failure paths: a failed commit is reported only to its caller, most callers go on, and nothing tells the person or the guard, so a full disk drops turn output while agents keep working; and when cutting back a failed append also fails (always on Windows, because the handle is append-only) the index offsets are wrong from then on and are saved into `index.bin`. Second, the store's index is visible to readers before the model has applied the lines, and the view revision is computed from it, so a view can be marked current with stale content. Third, streamed-text frames are dropped on broadcast lag with no resync. `docs/store-checkpoints.md` describes the removed JavaScript store: there is no `store.db`, no SQLite transaction, no held writes after a failed rollback, no disk-full queue; the Rust store guarantees only "appended and fdatasync'd before the ack, derived state rebuilt from the log or from validated checkpoints". The checkpoint task also rewrites the whole index and model every two minutes whatever changed, against `docs/STARTUP.md`. Tests cover the store's torn-tail and index cases well, but no test fails a write through the hub's writer.

## Missing tests
- A write that fails inside `Hub::writer` (a store whose append errors): every caller of the batch gets `Err`, the model and observers saw nothing, `commit_failed` got the base, the next commit gets the same first line number and succeeds. The test named `a_transform_adds_events_to_the_same_batch_and_is_told_of_a_failed_write` never fails a write.

## Style nitpicks
- `Hub::revision` is `async` with nothing to await.
- `note_bad` (store.rs:49) reads the whole `bad-lines.jsonl` for each bad line: quadratic on a badly damaged log.
- `Store.bad` is fixed at open; a torn fragment closed off later is not counted in the saved index header.
- `commit_many` is documented to return "the log's new length" (HUB-API.md) but returns the line of the caller's last event within the batch.
- `stamp.rs` (message time stamps) and `ckpt::stamps` (fold hashes) share a name for unrelated things.
- `Row.kind` is `&'static str` while every other field is a `String`; `Model::row` takes a `thread` argument it discards (`let _ = thread`).
- `fold_inputs.rs` carries `#![allow(dead_code)]` for the whole file because `build.rs` includes it; the allow hides real dead items there.
- `delta::apply` is public non-test code that unwraps on a malformed path; it is only the test oracle.
