## Summary
The unit answers the desktop client's `view.open`, `view.update`, `view.action` and `view.page`: it validates the envelope, reads the thread's page from the model, hands the presenter a session rebuilt from a per-connection `ViewActor`, and returns a whole or keyed-delta reply; it also holds the pure action functions (composer, select, Diff and Review pages, thread buttons), the reference popup, and the search index. The pure functions are small, well tested against recordings of the old hub, and build every request text with a JSON encoder, so I found no injection path. No action here writes events or checks who the caller is: a view action only returns commands the same client then sends as ordinary RPCs, and `Caller` carries no device identity, so authorisation is the connection's admission and nothing else. The actor is released on disconnect (`Hub::detach` calls `forget`), with a small leak through answers that arrive later. The main risk is the session itself: it is the store for bulk results (a thread's whole diff text, review reports), it only grows, and it travels whole in every request and full reply, so it can pass the 512 KiB frame limits on both sides and lock the desktop client into a reconnect loop. Second, a missing or deleted thread is answered as a retryable PRESENTER_UNAVAILABLE instead of STALE_VIEW, so clients never learn the thread is gone. Third, several per-request reads run under the hub-wide model lock without a bound (the subagent view's 4,000 rows, the context walk on older pages). Search and references are ASCII-centred: the index misses words past the 48th character of an unbroken run (normal in Japanese text) and names without ASCII letters cannot be referenced at all. Much helper-era plumbing remains (unbound reads, the window helper, the mech sync gate, the language refusal) that no code path can reach or use. Tests cover the pure functions well and `view_request` itself hardly at all.

- gpui client: `View::request` sends the whole session and the reconnect arm keeps it (native/gpui/src/hub.rs:115 and :186). Is there any bound on the request's size, and why is `viewControl` not offered when the hub can segment (native/host/src/session/mod.rs:196)?
- wire: the inbound limit is 512 KiB a message (native/host/src/wire/mod.rs:201). Is that meant to bound a view request that carries a session, and what does the client see when it is passed?
- files: who deletes an uploaded attachment that was detached, never sent, or lost with its session (native/host/src/session/thread_actions.rs:92, native/host/src/files/attach.rs)?
- data: `search` passes `q` to `search_for` with no length bound, where `find` has one (native/host/src/data/ext.rs:356 and :194).
- agents: does `turn.start` itself enforce the 128 KB message bound? The composer refuses only when the client sets `@draft.bound` (native/host/src/session/composer.rs:157).
- hub: `request` records replies of `files.dir`, `pdf.page`, `mech.*`, `git.status` and the settings reads for a presenter that ignores them (native/host/src/hub.rs:588-599); `FAR_READS` is not cleared on detach and `far_replied` can run for a client that has gone (native/host/src/hub.rs:606).
- agents: the `thread.btw` task calls `record_answer` without checking the client is still attached (native/host/src/agents/mod.rs:457).
- model: `latest_context` walks back with no limit (native/host/src/model.rs:223); is a cap acceptable to the window's context rule?
- auth: `Caller` holds only `gen` and `client` (native/host/src/hub.rs:634). Is it intended that no handler can tell a paired device from the hub token, so every admitted connection may do everything?
- commands: is the part of a thread id after the last `-` unique among threads? The `>` popup uses it to tell same-titled threads apart (native/host/src/session/mention.rs:114).
- files: are diffs produced with `core.quotePath=false`? `pages::parse` keeps a quoted, octal-escaped path as the file's name (native/host/src/session/pages.rs:40).

## Style nitpicks
- `#[allow(dead_code)]` on the modules composer, dispatch, patch, select and slash (mod.rs:13-17) hides unused items: `popup_word` (composer.rs:38), `Facts::account_params` (composer.rs:249).
- `B::new` defaults a missing `rid` to 1 in pages.rs:157 and thread_actions.rs:41; the composer and select default it to 0.
- Stale comments: composer.rs:43-44 says the popup rows "came from helper" while mention.rs computes them; actor.rs:35-37 lists as a limit what `set_bot` now does; the doc comment of `window_for` sits above `sub_log_for` (mod.rs:212-215); thread_actions.rs:167 ("Ui.fork.with") sits above the lock arm, not the fork arm.
- mention.rs is pulled in with `#[path]` from composer.rs:7, so the file `session/mention.rs` is the module `session::composer::mention`.
- `/secret a b` names the box by the last word (`slash::token`, composer.rs:79), not the first.
- `text.get(12..)` in `queue_json` (composer.rs:227) is the length of "[Backplane] " written as a number.
- `snippet` counts the hit's place in the lower-cased text (search.rs:28); lower-casing can change the number of characters, so the window can sit a little off.
- `sub_log_for` keeps the machine's name for the life of the process (mod.rs:218).
- A malformed view request (wrong types, a target with an extra key) answers STALE_CONNECTION, the same code as an old connection (mod.rs:106).
