## Summary
The unit is the design review (`review/`: file checkers for fab limits, BOM, outputs, assembly and mechanical parts, the run that adds DRC/ERC and a stock-KiCad second opinion, the on-save policy, agent-judged datasheet checks, markers in KiCad) and the BOM lane (`bom.rs` pure grouping and rules, `bompanel.rs` the live panel, `bomedit.rs` edits through KiCad's API, `parts.rs` stock lookups through the pcbparts MCP server). The pure parts are careful and well tested: `bom.rs` is checked against recorded oracles, `stockdrc.rs`, `markers.rs`, `policy::next` and the `parts.rs` limiter and book have direct tests, and edits never write KiCad files by hand, so there is no escaping risk on the write side. The weak side is the glue around them. The BOM panel has four defects a normal session meets: sheet files are read from any path with no size or type check, the live read from KiCad covers one sheet document, a published BOM over 64 KiB is refused without notice, and the watch ends after 30 minutes while the panel is still shown. The review's verdict is weaker than its documentation says: a save-scope run is accepted as the run for an order, a DRC that could not run still gives `ok`, agent-judged must-changes do not reach the verdict, and the BOM lines it reads can be stale. Several checkers parse KiCad text by substring and tab layout or by fixed CSV columns, which gives silent misses on older files and a false must-change on KiCad's own placement format. "The design's folder and project" is resolved in five different ways across this unit and its callers, which is behind the multi-board and worktree mismatches. Nothing here corrupts the event log or a design file by itself; the worst design-file risk is a headless BOM edit written under a KiCad that did not answer. Lookups send every part number of a shown design to a third-party service by default; nothing else of the design leaves.

## Cross-unit questions
- Answer (a): confirmed, and the BOM path is the more exposed one. `bompanel::read_sheets` (bompanel.rs:98) runs for every project a client shows and for every review; see the first finding. `kids` accepts absolute paths and `..` (plotread.rs:119), and `.backplane.json` can name an absolute board or schematic (kicad/project.rs:56).
- Answer (b): the `design_review` tool uses `canonical::design_root(files::root_of(thread))` (review/mod.rs:359), so the main checkout for a hardware project. The Fab panel uses `root_of_pro`, which also applies `design_root` (fab/panel.rs:47). `order_review` uses `world.cwd(thread)` (agents/world.rs:173: the project root only when `kicad.main.<thread>` is "on"). - Answer (c): no. The review reads DRC through kicad/findings.rs: `severity_of` (findings.rs:148) maps `"excluded": true` or severity `exclusion` to `excluded`; `counts` keeps them apart; `run_json`'s verdict and `must_lines` count `error` only; review.md lists error, warning and info; markers skip them; `stockdrc::extra` drops stock's exclusions. The release gate's reader (kicad/checks.rs:37 `make`) keeps KiCad's `severity` and ignores the `excluded` flag, so the two disagree; findings.rs is the behaviour to keep.
- Answer (d): not in this unit: the design review files no comments (its findings go to the Checks list and `.backplane/`). Review comments are `ActivityLogged` events of tone `review` on the thread, folded by kicad/review.rs.
