## Summary
`mcpx/` keeps one list of MCP servers per hub (`<home>/mcp/servers.json`), reads pasted and imported configurations, makes each provider's form of the list, starts stdio servers through the hub's own wrapper (`--mcp-run`), checks servers, and serves Settings > MCP and the agents' `mcp_` tools. `md/` is the chat's Markdown (a port held to recorded cases) and a second, GitHub-style document renderer (pulldown-cmark plus an HTML allow-list) whose output is JSON nodes, never HTML text. The pure parts (parsers, generators, page rows) are small, readable and tested; `svc.rs`, the gating in `tools.rs`, `act.rs` and the wrapper's main loop have almost no tests. `toml.rs` is a reader only and `gen.rs` writes no file: nothing of the person's own agent configuration is written, configurations go on argv, in the environment and on stdin. The main risks are at trust boundaries. The answer to the MCP reviewer's question is yes: `backplane/mcp_spec` and `backplane/mcp_headers` hand out vault values in clear to any holder of a thread URL, unmasked and unrecorded, and the URL stays valid after its process is gone. An agent can widen a server's scope and turn its tools back on without the person's card, and "Keep in sync" lets a file in a project folder change what every agent runs with no confirm. Turned-off tools are not enforced for remote servers on the ACP agents. In `md/doc.rs` a `%` before a multi-byte character panics inside the policy state lock, and unbounded HTML nesting (like unbounded nesting in `toml.rs`) overflows the stack and aborts the hub. The desktop page stops updating when `info["mcp"]` passes 64 KiB.
