## Summary
The unit links hubs (a `bp1:` invite or a machine code approved by the person), keeps the peer table folded from `PeerSet` and two setting families, signs requests between hubs with HMAC-SHA256 over `timestamp.body`, finds machines, and keeps the project registry. The handshake is careful about the obvious cases: secrets are 32 random bytes kept in 0600 files, never on argv; ids that name files are restricted; signatures are compared in constant time; curl follows no redirects and is limited to http(s); a pasted invite is not owner-trusted until the person says so; every outbound call to a peer's address is filtered to verified or own links. The weak points are in what the trust is bound to. Owner trust is a setting `peer.own.<id>` that outlives the link, so a later link under the same id inherits it without approval. The signature covers neither route, method, direction nor peer id, and one symmetric key signs both directions. Pairing by address sends the long-term link secret in an HTTP response body, and plain `http://` is accepted for any host, so off the tailnet the secret is readable on the wire. The copy guard sits in `botnet::curl`, but `botnet::signed` hands a call to the reverse tunnel before it reaches that gate. The registry is keyed by a self-declared host name, writes a whole snapshot into the append-only event log on every change and every ten minutes (also on a hub with no other machine), and its in-memory cache is rebuilt from partial sources. Tests cover the pure functions and the happy handshake well; `registry.rs` `put`/`serve`/`tick`/`forget`, unlink followed by a new link, commit failure and the copy guard for peer traffic have none.

- `signed_in`: a signature made for one route refused on another; a request of this hub's own refused when sent back to it; a signature with a timestamp 300 s ahead refused 301 s after it was first accepted.
- `registry::put`, `serve`, `tick` and `forget` have no test at all: an unchanged put writes no event (also after 600 s once `seen` leaves the log), two machines with one name, a put naming another machine's rows, `forget` after `machine-rename`, the cache when the home answers code 0, a `registry.put` received on a hub that is not the home.
- `link` and `join` with a failing commit (no 200, invite not spent, no "linked" reported), and two `/bots/link` requests in flight for one invite.
- A copy (`BACKPLANE_COPY=1`, in the child-process style of `copy_outs.rs`): `to_peer`, `post_json` and `link_up` reach no listener, a live tunnel poll receives no call, `/far/push`, `/far/log` and `/bots/link` are refused.
- `PeerTable::start` with a failing `store.range`: the table is not marked replayed and no checkpoint is written; and a start from a checkpoint followed by buffered commits.
- `botnet::args` and `link_up`: the arguments hold `-g` and `-q`; a response without Content-Length larger than the limit is cut.
- `machinespage::act`: remove, mine, rename (an empty or taken name) and the `bp1:` branch of `machine-pair` have only e2e coverage; `Peering::introduce` with an address that differs only in port, and with IPv6 literals.
- `machines::host`, `port` and `loopback` with IPv6 literals, userinfo, `127.example.com`, `0.0.0.0`.
- The finder: while a link is missing, the number of probes per minute stays under a bound (a counter in place of curl).
