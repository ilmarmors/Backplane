## Summary
These six files are the client's dumb renderers for hub-described rows (Settings, Setup), the Accounts page, the pairing screen, hub switching and the project page/folder picker. Secret handling is good: vault fields are never `bfield`s, never taken from the hub, never in Debug output, and `Secret(..)` wraps every request that carries a code or key; sign-in code boxes are masked. The pairing screen follows docs/pairing.md (an outside link only asks, Cancel first, a failed exchange leaves the old pairing, relaunch strips `--pair`/`--url`). Hub switching restarts the process, so nothing carries over from the old hub, but the automatic failover to the home hub does not restart and does not reset client-side state. The main risks: a per-frame `Box::leak` on the project page, an unconfirmed destructive "Forget" of a hub credential, an unchecked URL scheme on the sign-in "Open" button, and (answering the cross-reviewer question) there is no second route for the four typed Voice/Ring fields, so on the desktop their Save buttons run with an empty draft. Tests cover the pure helpers well; the stateful flows (sync, failover, offers) have none.

## Missing tests
- Failover (`Event::Using`) with Accounts open and a typed vault value: state is reset or at least refreshed.
- `hubpick::offered` with `doing` set and no reply: a later offer is still handled (after the fix).
- `pair::confirm` / `incoming` while `busy`.
- A render-level or helper test that a project page's viewer-button ids are static (no allocation per frame).
- A test that a Settings row Save with a typed field sends the field text (or that every field name the hub's rows emit is accepted by the `bfield` whitelist; a cross-crate fixture of row field names would catch `vphrase` and `vfix`).
- `accounts::attempt_panel` Open with a non-http URL does nothing.
- `Echo` with 33+ rapid texts (the log is capped at 32) followed by a late echo of the oldest.
