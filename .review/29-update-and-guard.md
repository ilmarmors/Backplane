## Summary
The unit is the hub's updater (`update/rel.rs` rules, `run.rs` fetch and stage, `svc.rs` the service) and the guard (`native/guard`, the `backplane` program: start, probe, ladder, rollback, safe mode, rescue, the CLI and `backplane pair`). The pure parts are careful and well tested: versions and channels, the signed manifest (the signature is checked over the exact bytes before they are parsed; tag, version, channel, file name, checksum and size are then held to the tag that was offered; nothing older or equal is offered), the listing of an archive before it is unpacked, one rename into `builds/<tag>`, and the ladder in `plan.rs`. The risks are in the shells around them, which have no test in the crate: `Updates::pass`, and `Guard::one_run`, `go` and `rescue`. The most serious: rescue cannot be reached from another device after a start that dies early, because the hub deletes the address list at each start; probation reacts only to a crash, not to a refusal, a machine error or a clean exit; a build can be promoted to good while its probes fail; the updater's only hold is "no running turn", asked once before a long download, and Update now can stay armed. On the security side the URL from the unsigned release list reaches `curl` unchecked, rescue tells its failure reason to anyone, a signed control request can be replayed (the rescue cache is rebuilt every two minutes, the hub has none), and the hub's own check accepts an empty link secret. A `build` named in a remote control request is passed through by the hub unchanged; the guard holds it to the ids in `guard/control` (builds that ran here and answered with the control route), to a `backplane-hub` on disk and, for an update, to not being in BAD (run.rs:199-206, plan.rs:133-139); a local request is taken as given, and `Builds::dir` joins it as a path (store.rs:84). Process control goes through the child handle everywhere except `end_orphan`. Rows marked (Question a) to (Question h) answer the questions put to this unit.

## Missing tests
- Rescue's addresses after a start that died before the tailnet listener bound: with only the loopback line in `listeners`, the last known addresses are still bound (the choice as a pure function).
- `plan::next_on` on probation with `End::Refused`, three `End::Machine` and repeated `End::External`: each goes back to the build before.
- The probe step of `one_run` as a pure function: no promotion on a missed probe; promotion after 60 s of well probes; folding holds the clock; six misses kill; lost parts and identity on probation.
- `Updates::pass` with injected fetch, unpack and turn count: `forced` is cleared when the check fails, finds nothing or a pass is already working; a turn that starts during the download holds the request; the wish is carried out when the turn ends.
- `svc::curl`: a URL that starts with `-`, `file://`, `gopher://`, or `http://` under an https feed is refused before any process starts.
- `rescue_handler`: a signature accepted by one handler is refused by the next one made for the same guard; `/healthz` without a credential carries no `why`; many slow connections do not grow the thread count without bound.
- `take_request` drops a request whose `at` is old; a request left on disk is not carried out by a guard that starts later.
- The hub's `own_machine`: a live, verified link with no secret file is refused (an empty HMAC key must never verify).
- `Guard::short` on `v0.16.0`, `v0.16.0-beta.2` and `v0.16.0-nightly.20261114.1`.
- `stage` with a leftover `.stage-<tag>-<other pid>`: the next start removes it; `prunable` and the sweep agree on dot names.
- The arguments `headless` and `start_guard` build (as pure functions): `--log` is there and survives a start from `launch.json`.
- `end_orphan`'s reading of `hub.lock`: "0", "4294967295" and junk signal nothing.
- `faults.sh`: a start that is still folding when `BACKPLANE_GUARD_BOOT` passes; an update whose hub exits 78; a hub that exits 0 at once; a stale request file at guard start.
- A guard with `BACKPLANE_COPY=1` and a shared builds folder writes neither BAD nor `CURRENT` there.
- `Dir::ask` on a filesystem without hard links: a clear refusal or a fallback, not "cannot reach the guard".

## Style nitpicks
- `update/boathub.rs` (the cost of the always-on Boat) has nothing to do with updates.
- docs/HUB-RESILIENCE.md: "pausing 1, 2, 4 s" (the code pauses 1 and 2 s, the third failure falls back); "native/host does not build on Windows yet" against the Windows code and CI; "`peer.own.<id>` is `pair` or `owner`" (the code also takes `approved` and `tailnet`); "gives it back when under 64 MB is free" (only at a hub start).
