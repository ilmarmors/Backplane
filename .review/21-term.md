## Summary
The unit is the hub's terminal actor (ptys on Unix and ConPTY, a VT emulator, chat terminals for agents, an offset stream for phones) and the browser lane (one helper process, the `preview_*` tools, take-over, teach recording and task runs). The emulator and the pty code are careful: every index in `vt.rs` is clamped, parameters, OSC strings, replies, queues and scrollback are bounded, and I found no panic path from program output. The weak part is lifecycle: a terminal ends only when its pty reaches end of file, nothing ends a terminal with its thread, client or far view, and a restart tells clients too little, so shells leak up to the hard cap of 64 and cards show the wrong state. One download path is broken outright: a file over 32 MiB can never reach the client. Rules that the actor states for itself (quiet terminals, the done mark, the summary format) are enforced at one entry point or on one chunk only and fail at the others. The browser lane passes agent URLs (including `file:` and loopback) to a helper that shares one signed-in profile between all threads. The teach and task code (about 60 KB) is not reachable from any client or agent in this tree, so its bugs are latent. Any authenticated client may open a shell by design (every pairing is full access, `data/term.rs:1-3`); `TermRpc` never looks at the caller. Answers without a finding of their own: (b) `term.input` is bounded per pty, not per client: 256 queued writes of at most 262,144 bytes each (64 MiB a terminal), more is dropped silently and the request still answers ok; (c) yes, `run_with` pushes a `reset:[cols,rows]` frame to every client on `term.restart` (`mod.rs:241`), but only when the run really starts, and without `state`, `g` or `o`.

## Improvements
| Priority | Area | Proposal | Why | Effort | Trade-off |
|---|---|---|---|---|---|
| P1 | Terminal lifecycle | One owner rule for every terminal: end it on ThreadDeleted, archive and settle; idle timeout for shells no client shows; treat the leader's exit as the end. | Fixes the slot leak, the stuck terminal and the dead panel in one place. | M | A long job in an unwatched panel shell needs a pin or a longer timeout. |

## Missing tests
- A shell that exits while a background job holds the pty (`sh -c 'sleep 30 & exit 0'` as the leader): the terminal must reach `exited 0` and free its slot, and `kill` must end what is left.
- `/browser-download` with a file over `PIECE` (32 MiB): the whole file reaches the caller.
- `term.restart` of an ended terminal: a frame that says `running` for the new run reaches every client, after the reset and after any frame of the old run.
- The phone protocol and quiet terminals: `term.write`, `term.resize` and `term.stop` with a `q:` key are refused, and no client receives a frame for it.
- Two clients that resize the same terminal to different sizes: the number of resets is bounded.
- `terminal_open` with a multi-line command and no title: `parse_summary(summary(...))` gives back the size and the command.
- The done mark split over two `fed` calls: the state becomes `done N`.
- Thread delete with a running panel shell and chat terminals: nothing of that thread is left in `shells`.
- A property test for `Vt`: random bytes mixed with random `resize` calls never panic, every row has `cols` cells and the screen has `rows` rows; a second one for `snap`: feeding the snapshot of any reachable screen to a blank `Vt` gives the same `text`, including overlong UTF-8 input.
- `terminal_open` at `MAX_SHELLS` and on a failed spawn: the tool's answer says it did not start.
- `task_end` after a pause that timed out: the run is `Ended` and the `MAX_RUNS` sweep removes it.
- A restart of the hub with files in `<home>/browser-downloads`: they are removed or listed again.
- Windows: a terminal that exits by itself leaves no entry in `plat::proc::KEPT`.
