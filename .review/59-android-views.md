## Summary
Six files of the Android data/1 app: the screen tree and thread view (DataViews), the viewer tabs (DataViewer), a Kotlin port of the hub's terminal emulator (Vt), a hand-written Markdown renderer, and link detection and tap handling. Vt.kt is a faithful, line-for-line port of vt.rs (state machine, bounds, replies, keys, paste); I found no divergence beyond a missing lower bound in `lines()`. Link handling is conservative: only http(s), mailto, tel, backplane:// and bppath: are acted on, and the last two go through the hub's `link.resolve`. There is no WebView. The main risks are in the Markdown renderer: images are fetched from any address an agent writes (tracking, LAN requests, no size cap), nesting and bracket runs are unbounded so a crafted message can hang or crash the app every time the thread is opened, and everything (parse, bitmap decode) runs on the main thread during composition. Several smaller issues are in the viewer tabs (unbounded downloads and decodes, polling, stale taps) and in DataViews (shared global link context, an early return that drops list state, a request per new entry). There are no tests for the Markdown parser's hostile input in the files reviewed.
