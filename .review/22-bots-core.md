## Summary
The unit is the bots lane's core: the `bots.*` requests, the bot MCP tools, the world folded from the log, room posts and their guards, the status plane text, inbound webhooks and the ring's front door. The code is dense but consistent: one async lock (the world's) is held from decision to commit, ids that become file names are checked (`safe_id`, `botnet::safe`), the backup shell script takes its values as positional arguments, and every one of the 28 tools in `tools.json` has an arm in `tool_decide` and the reverse. The main risk is that same lock: three bot tools make signed HTTP requests to linked machines while holding it, so one sleeping machine freezes the bots lane and every non-person delivery in the hub for up to 15 s per call. Deleting a bot is only a `BotDeleted` event: its routines keep firing, its webhook secrets stay on disk, nothing on disk is removed, and the hub itself does not refuse deleting the uberbot. Webhook authentication is sound for the timestamped signature, but the GitHub path has no real replay protection, the replay key is consumed before delivery, there is no rate limit, and the ring front forwards unauthenticated requests to another machine before any check. The focus question about a bot's space page has a simple answer: no route serves it and no client shows it, so it shares no origin with anything; `space_page` only stores HTML in the log. `gate.rs` is the room guards (rate, chatter, circular, budget, backstop), not a permission system: what a bot may do is decided only by `World::run_bot(thread)`, and bots are not isolated from each other. Several world maps grow without bound. Tests cover the happy paths well (webhook signatures, create, say, post, tools parity with the JS hub) and miss the failure and concurrency paths listed below.
