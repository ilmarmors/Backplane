## Summary
The unit holds the device registry (`pairing.rs`), the `/auth/*` routes, the machine-pairing flow (`pairflow.rs`), the tailnet and local-network listeners, request signing and a QR encoder. The registry core is sound: 128-bit invitation and device secrets from the OS generator, only SHA-256 hashes on disk, one mutex around every operation with the file written (temp, fsync, rename, fsync of the folder) before memory changes, so two concurrent enrolls of one invitation cannot both succeed; the eight-character code has 40 bits and is held to 10 tries a minute per address and 200 hub-wide; the separate error answers tell a caller nothing unless it already holds a valid secret; revocation closes live sockets through one shared path with a race guard (`retired`). No credential-free bypass was found: neither the tailnet nor the LAN listener grants anything but the one `trusted` flag, whose only reader is the Google OAuth hop. The QR encoder matches the standard algorithm for all 40 versions by inspection, but its tests stop at version 7. The main risks are around the core: machine pairing has no key agreement, so over plain `http://` the code, the check digits and the link secret travel in clear and a link secret means agent turns and shells on the hub; availability is coupled to storage (a `lastSeen` stamp that cannot be written answers 401, which every client reads as "revoked"; a failed `/dev/urandom` open panics under the registry lock and locks every device out until restart); both listeners bind once at start and never retry; a registry the hub cannot parse turns the whole net lane off while its devices keep access and cannot be revoked; the replay cache forgets by arrival time and signatures do not cover the route. The owner-trust machinery (`OWNED`, `own_hosts`, `own_device`, `owner_peer`, `owner::trusted`) is computed on every tailnet connection with a `tailscale whois` subprocess and read by nothing. `docs/pairing.md` still describes the older hub-wide ten-a-minute bucket and "fail closed".
