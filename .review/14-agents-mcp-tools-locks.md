## Summary
This unit is the loopback MCP server each agent process is given, the tools that act on threads and accounts, the design-file rules for hardware threads, the named locks, the agents' own fold of the log (`World`) and the side-by-side checks. The lock code is careful: one record per name written whole, every transition under one mutex, a grant written before it is told, restart and flock interop tested. The MCP server is small and bounded (4 MB body, 16 KB head, 256 connections, a constant-time key compare), and the per-thread key is an HMAC of a random secret made at each start, not of the pairing token. The main risks are about who holds which credential. The answer to unit 02's question is yes: nothing keeps an agent out of the hub's home; the hub hands every agent the home's path in its environment, a bot's folder is inside the default home, and the shipped lock helper reads `<home>/token` itself, so every approval, rule and charter the hub enforces holds only against a cooperative agent. The MCP URL, which is the whole credential of a thread, is on the agent's command line, where every local user can read it and then run commands as the hub's user. The enforced-rule gate can be opened by the agent it gates with one `thread_send` to itself, and it looks at only the newest 49 rows, so it also refuses wrongly in long turns. In the locks, a shell helper's exclusion ends 90 s after the helper dies although the docs promise a guard that does not exist, a design commit can take another thread's held document, and messages are sent to threads while the lock mutex is held. Tests cover the happy paths of locks and the key check well; the HTTP edge of the MCP server, the rule gate's provenance and the cross-project checks have none.
