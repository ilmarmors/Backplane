## Summary
The unit is the order server: a FastAPI service that prices parts from features a client sends (`/v1/estimate`), takes a multipart upload of manufacturing files, measures them in a child process and prices them through a private fab pack (`/v1/quotes`), opens Stripe Checkout (`/q/{id}`), and lists paid orders for an operator (`/admin`). The basics are done with care: the price and currency never come from the client, every file is held to the manifest's SHA-256, paths and zip entries are checked well, tokens are stored hashed and compared in constant time, the pages escape everything under a strict CSP, payment is confirmed by asking Stripe, and the systemd unit is sandboxed. The main risks are availability and the accuracy of the money, not data theft. `POST /v1/quotes` parses a URL-encoded body with no limit, so one or two 50 MB requests can run the service out of memory. The analysis children's memory limits add up to more than the unit's `MemoryMax`, and a quote interrupted by a restart is retried without a count, which can become a restart loop. The shared budgets (the global daily quote cap, the distributor's daily calls) can be spent by one client, because they are counted before validation or keyed by the install id the client chooses. On the money side, measured values are not checked for range or finiteness before pricing, a pack answer of `{problem}` for shipping crashes pricing, duties are zero for a duty-paid country outside the tables, and pilot (test-mode) orders are stored and listed like real ones. The analysis "sandbox" is resource limits only: the child runs as the same user with the network open. Personal data and quote rows are kept without end. The tests cover the upload checks, taxes and the distributor budget well, but almost nothing of `pay.py`, the admin endpoints, solids, DXF or the limits over HTTP, and nothing runs `order/tests` automatically.

## Cross-unit questions
- Answer to unit 32's question: yes, `POST /v1/quotes` holds each file to the manifest's sha256 (package.py:198), and refuses a file that is not listed, sent twice or missing (lines 194-209). It does not dedupe: every POST makes a new quote row and folder, which costs budget and disk but commits no money. `GET /v1/quotes/{id}` answers 404 only for a wrong token; rows are never deleted, so an accepted quote stays readable (later as `expired`) unless the database is lost.
- native/host/src/settings/order.rs:402 (unit 32): `poll` treats every 5xx as transient for all 600 rounds. A quote whose GET always answers 500 (a NaN in the stored result) keeps the thread waiting about four and a half hours. Should repeated 500s for one quote end the wait sooner?
- native/host/src/settings/order.rs:270 (unit 32, `ask_detail`): the approval says the files "are kept only to make what you order". The server keeps an unpaid quote's files 7 days and its row (IP address, install id, manifest, BOM result) without end. Which of the two is to change?
- native/host/src/settings/fab.rs:205 (unit 32): `est_got` reads only `error`. The server also answers `{"detail": ...}` (Starlette's own errors) and nginx answers HTML (413, 503). Is "the order server said 400" enough there?
- native/host/src/settings/fab.rs:13 (unit 32): the default server is a bare IP address with a six-day certificate renewed by `fab-cert.timer`. If renewal fails, every hub loses ordering within days. Does the hub say why, and does anything watch the timer?
- scripts/dev-build.sh:112 and scripts/land.sh (unit 35): should `order/fabsrv/catalog.py` be an input of the hub gate key, and should landing run `order/tests` when `order/` changed?
- native/host/src/agents/prompt_text.rs (unit 51, the buy prompt): can an export put files under a folder whose name ends in `.d`? `admin_files` (order/fabsrv/app.py:275) leaves such folders out of the operator's zip, since it takes them for unpacked archives.
- The fab pack (`FAB_VENDOR`, private): does `shipping()` return `price` beside `problem`; for which countries does it say `ddp: true`; does `library()` send BOM strings to a network service, and with what time limit; what does `estimate()` do with NaN or negative features? None of it can be reviewed from this repository.

## Style nitpicks
- `money()` exists three times with two meanings: pricing.py and pages.py format dollars, sourcing.py parses a price.
- `estimate.catalog_max()` returns the constant 20 that `package.MAX_PARTS` also holds.
- `Gerber._num` takes an unused `axis`; `layer_role`'s layer numbers are never used, only their count; the default `ship` dict's `"taxes": None` is read nowhere.
- store.py's schema comment lists a quote status `expired` that is never stored.
- nginx.conf line 2 says deploy.sh fills in HOST; the file has no placeholder and deploy.sh copies it as it is.
- config.py: the default `PAUSED_NOTE` carries a date ("As of November 8"); `TRUSTED_PROXIES` is split without stripping spaces.
- `vendor_api.available()` imports a failing pack again on every `/v1/health`.
- tests/conftest.py makes a temp dir with `mkdtemp` and never removes it.
- `sourcing.price_at` returns 0.0 for an empty price list, so a stocked part without price breaks is free.
- `limits._hits` gets two keys for each new install id and keeps them a day; nginx's zones count each IPv6 address, the app each /64.
- `pages.admin` formats the date with `%-d`, a glibc extension.
- `admin_files` builds the zip in memory on the event loop.
